# 非原版优化记录

本文件记录 Festival 3.1 C++ 原版没有、Rust 移植额外引入的优化。这类优化不作为
移植的一部分写进 `rust-rewrite-plan.md`；计划文档只保留移植本身和为对齐 C++ 语义
所做的修正。

约定：

- 实现级优化不改变任何可观测行为：shift/推拉距离矩阵、走法、死锁判定和
  `solutions.sok` 必须与 C++ 一致，由差分测试或等价性论证保证。
- 启发式优化（搜索顺序、评分或方案选择）可以改变 `solutions.sok`，但必须保持解
  合法：`--validate` 全部重放通过，并在条目中记录 moves/pushes 变化与配对基准。
- 每项优化给出性能数据；原始计时、复现命令与校验和记在 `reference/BASELINE.md`。
- 记录粒度是“一次可独立回滚的实现选择”，性能回归时可直接定位到对应条目。
- 已实测否决的方向统一记录在文末[已否决的优化方案](#已否决的优化方案)；重新尝试前
  先核对对应的“重新评估条件”。

## 2026-10-29 双连通块标注 shift 矩阵

**问题**：`Graph::build` 的 `init_shift` 对每个空格临时放箱，再用一次 BFS 标记四周
玩家所在分量，单次构建是 O(空格数 × BFS)，占 build 时间的 96–98%。XSokoban 1–20
单核 10.4 s 中 1.89 s（15,097 次 build），XSokoban 18 策略 A 2.37 s 中 0.76 s
（6,098 次 build）。

**方案**：每次 build 做一次迭代式 Tarjan 双连通分解（显式栈、按
`level.index_num()` 的 `u16` 数组、遍历所有分量、scratch 挂在 `Graph` 上跨 build
复用）。某格被箱占据后两邻格仍连通，当且仅当两条关联边属于同一个双连通块，于是
shift 边可逐对 O(1) 判定；唯一的调用点 `bfs::mark_connectivities_around_place`
随之删除。

**等价性**：块是 2-连通图或单桥；删去一个顶点后块内其余顶点仍连通，反之若两邻格
在删格后连通，则该路径与两条关联边构成经过该格的环，两条边必同块。墙格、越界格和
`active` 过滤的处理与原实现一致。新增逐格逐方向的暴力 BFS 差分测试（6 个手写盘面 +
300 组随机加墙）覆盖割点、桥、多分量等情形。

**结果**（同日交替配对，1 核）：XSokoban 1–20 9.95 → 8.54 s（−14.5%）；XSokoban
18 策略 A 2.62 → 1.74 s（−33.4%）；Microban 1–155 10.57 → 8.88 s（−16.0%）；
8 核 Microban 13.27 → 11.91 s（−10.3%，受取消时机影响，仅供参考）。临时计时（已
移除）显示残余 `Graph::build` 从 1.89 s 降至约 0.25 s（XSokoban 1–20），约占整体
2–3%。

**验证**：120 个单元测试、clippy/fmt/deny 通过；XSokoban 1–20 为 18,143 moves /
5,466 pushes，Microban 155/155 为 22,486 / 5,920，与基线一致；`solutions.sok`
逐字节相同（仅时间戳），`--validate` 全部重放通过。原始计时与校验和见
[`reference/BASELINE.md`](../reference/BASELINE.md#biconnected-shift-follow-up-2026-10-29)。

**v0.1.1 全量复审**（同日新旧二进制，1 核）：XSokoban 90 关 160.6 → 102.1 s
（−36.4%）。第 1–28、30–90 关的解与步数不变，只有第 29 关从 1277 / 298 变为
705 / 190：该关策略 A 的 75 s 墙钟配额（600 s 的 1/8）在新版内足够解出，旧版与
C++ 则超时后改用后续策略。因此“`solutions.sok` 逐字节相同”只对不受墙钟配额截断的
关卡成立；搜索本身（移位矩阵）的等价性仍由差分测试覆盖。

## 2026-11-02 多规划 forward portfolio

**问题**：反向 packing 通常能找到多个不同的停车方案，原版只使用反向搜索评分最好的
一个。固定预算下不同方案的前向开销差异很大：Microban 153 个 gate 内关卡中，方案 0
的合计扩张为 19,132，逐关最优方案的合计为 10,260，33 关至少有一个更优方案
（例如 Microban 146：6,822 → 175）。

**方案**：仅对 `ForwardWithBases` 且 `box_count <= 12 && index_num() <= 80` 的关卡
启用。按反向评分取前 512 个未死锁扩张，用 `get_parking_plan` 还原方案，与基准方案
去重后最多保留 4 个；每个方案独立执行 verify/reduce/OOP。每个方案在反向 tree 上探测
32 次扩张（显式 `--max-expansions` 时取预算的 1/8，夹在 1..32），探针使用反向
perimeter 的独立 `snapshot()`，避免互相污染；任一方案提前解出即返回。否则按
“最佳节点 `dist_to_targets` ↑ → frontier 最小 `dist_to_targets` ↑ →
`packed_boxes` ↑ → 方案索引”选择，并用剩余预算继续。探针扩张计入该阶段预算。

**结果**（同会话，非交替，1 核）：Microban 6.25 → 4.64 s（−25.7%），扩张
28,724 → 23,755（−17.3%），moves 22,486 → 22,366，pushes 5,920 → 5,926。
XSokoban 98.37 → 98.22 s（−0.2%），扩张 +0.3%：gate 内只有 9 个小关。

**验证**：Microban 155/155、XSokoban 90/90 全部解出并通过 `--validate`；123 个
单元测试与 clippy/fmt 通过。

## 2026-11-02 Hungarian 匹配 advisor

**问题**：FESS 的 advisor 集合没有直接使用“箱到目标”的全局最优分配代价；在部分
关卡上，packed/connectivity 主导的 advisor 会错过更接近完成的子节点。

**方案**：`matching_advisor` 仅对 `Normal | ForwardWithBases` 且
`box_count <= 12 && index_num() <= 80` 启用。用 `compute_match_distance` 计算当前
盘面与每个子节点的分配距离；跳过已扩张、以及 `packed_boxes` 低于父节点的子节点；
取分配距离最小者，平局时用 `is_better_score` 决出。它作为额外 advisor 加入
`is_an_advisor`，不替换原有 advisor。

**结果**（叠加在 portfolio 之上，同会话，1 核）：Microban 4.64 → 4.35 s（−6.4%），
扩张 23,755 → 21,925（−7.7%）；XSokoban 98.22 → 97.46 s（−0.8%，在噪声范围内），
扩张 −0.1%。

## 2026-11-18 P0–P3-A 实现级与并发热路径优化

对齐 C++ 3.1 默认 2 GiB/worker 搜索内存上限（`8fad35c`）后，大数组清零、锁争用与逐节点
临时拷贝成为主要瓶颈。以下四组共 12 个独立提交在不改变 C++ `Board::hash()` 数值与单核
确定性扩张数的前提下逐步消除开销：

- **P0（`ba5c1f0`、`dfa92e7`、`2617cf6`）**：`Tree::clear` 按已插入节点稀疏回填
  `hash_array` 槽位（阈值内避免整表 `fill(NONE_NODE)`），`boards` 改为按需惰性增长；
  `MoveHashData` 直接内联子 `NodeId` 消除展开与更新时的二次哈希探测；热点位集、房间连通度
  与棋盘 BFS 紧凑化。Microban 1 核 12.4 → 5.9 s（扩张仍为 21,925）、8 核 20.0 → 7.1 s，
  峰值工作集由 1.48 GiB / 7.16 GiB 降至 530 MiB / 3.67 GiB。
- **P1（`7093bfd`、`6cc567f`、`fe458f9`、`ed65afd`）**：在 `Graph::mark_box_moves_in_graph`
  复用双连通块判定玩家侧移并把泛洪队列迁至栈上；池化辅助死锁搜索的 `PositionSet` / `Helper`
  缓冲区，新增匈牙利匹配与冻结死锁快路径；跨 worker 共享只读 `RoomsDeadlockData` / `Mpdb`
  并转置热点初始化；`Perimeter` 改为批量查表、直接以 `u64` 作键（`IdentityHasher`）并用只读
  overlay 替代探针全表克隆。Microban 1 核 5.9 → 4.8 s、8 核 7.1 → 3.7 s；XSokoban 1–20
  1 核 11.6 → 8.6 s。
- **P2（`4b97757`、`6741669`、`f553b44`、`52838d7`）**：为 `RequestData` 建立开地址哈希索引、
  在 `Helper` 复用 `Graph` 与移动缓冲并对 packing 根去重；`Perimeter` 改用单把 `RwLock` +
  `AtomicUsize` 计数；`DeadlockCache::CacheEntry` 压至 16 B（带 `u16` 代数免全表清零）并增设
  无锁 2-way 跨核共享终局死锁缓存；任一线程解出后立即广播 `cancel` 提前中止其余线程，2/4 核
  改为原子动态认领策略（8 核保持槽位 7 绑定 `Dragonfly`）。Microban 8 核 3.7 → 3.4 s；
  XSokoban 1–30 8 核峰值 RSS 降约 160 MiB。
- **P3-A（`8f32adf`）**：将 `Board` 判等、标志位清除、箱数统计、序列化与 `apply_move_into`
  收敛至活跃行切片 `0..height * MAX_SIZE`，并在 `Tree::node_is_solved` 直接扫描紧凑字节槽；
  新增 `Graph::prepare_impossible_for_board` 与 `update_current_impossible_for_removed_box`
  （拉箱模式逐箱零开销，推箱模式每盘仅跑 1 次全盘 `mark_deadlock_2x2`、逐箱只重算周围 `4×4`
  个 `2×2` 窗口并回写最多 9 个脏格），原位临时摘箱消除每箱 3 次整盘拷贝；在 `patterns.rs`
  内联屏蔽 `DEADLOCK_ZONE`，并将 `diags`、`fixed_boxes`、`corral`、`biconnect`、`envelope`、
  `rev_hotspots` 中的临时 `Board` 拷贝与堆分配全部替换为栈缓冲与预索引。配对 ABBA 实测：
  XSokoban 29 单核无时限完整求解（`1,057,264` 次扩张完全一致）由 143.5 s 降至 119.4 s
  （−16.8%），Microban 1 核 4.99 → 4.85 s（−2.9%）、8 核 3.43 → 3.33 s（−3.1%），XSokoban
  1–20 1 核 8.95 → 8.72 s（−2.6%）。

## 已否决的优化方案

本节只收录已经实现或做出原型、并经过实测否决的方向。每项都给出当时的证据和
“重新评估条件”；未满足条件前不要重复投入，避免重蹈覆辙。

### 反向完整解复用

**设想**：反向 packing 已经解出时，直接把完整的 pull 宏序列反转成 forward 推步，
跳过前向搜索。

**实测**：在 XSokoban 29、XSokoban 15/16/18、Microban 145/146/153 等关卡上，反向
搜索确实以很少的扩张完成（例如 XSokoban 29 为 19 次），但完整解全部来自
BaseSearch。base 移动会把箱子从初始 base 删除（`to = -1`），反转后的路径不包含这些
箱子；`invert_pull_solution` 在第一个宏上即找不到合法正向路径，所有样本均失败。

**否决原因**：反向路径不保持初始箱子集合，直接反转在语义上就不成立。要修复就必须
重建被删除的箱子并重新规划，代价接近一次新的搜索。

**重新评估条件**：反向阶段改为纯保箱搜索，或已有可靠的反向 base 删箱 → 正向补箱
映射。

### MPDB2 取消 50 对上限

**设想**：去掉每个方向最多 50 个 push/pull 死锁箱对的截断，改为直接索引，以使用
全部两箱模式。

**实测**：对 245 个标准关插桩统计候选数与截断数，push 和 pull 两个方向的
`excluded` 全部为 0；实际表项远小于 50。

**否决原因**：上限从未生效，取消它不会改变任何搜索行为，只会增加存储和代码复杂度。

**重新评估条件**：新语料上重新插桩，确认某关单方向候选超过 50 且截断确实发生。

### 加法式 2-box PDB

**设想**：为箱对建立精确推距离表，把若干互不相交箱对的距离相加，作为比
Hungarian 单箱分配更强的下界或 advisor。

**实测**（Microban 155 关原型）：按目标对建表后，做“箱对/目标对都不相交”的贪心
加和，在 9/155 关得到的值超过真实解推数（例如 Microban 146 为 62，而实际解为
44 推），因此不是合法下界；合法的单对最大距离仅在 8/155 关比 Hungarian 分配更紧。
建表在 Microban 146 约 0.9 ms；对秒级关卡可忽略，但对毫秒级小关占比不可忽视。

**否决原因**：目标可互换，朴素的加和分解不保证与真实目标分配一致；合法形式又与
现有 Hungarian 分配高度重叠，且建表成本相对于小关求解时间过高。

**重新评估条件**：能对某类关卡给出可证明合法的目标划分，或找到不必枚举目标对的
模式构造，并证明其增量收益。

### 编译配置（历史）

PGO（`-Cprofile-generate` / `-Cprofile-use`）比 baseline 慢 3.5–5%，fat LTO
相对 thin LTO 无收益，均已否决；原始数据见
[`reference/BASELINE.md`](../reference/BASELINE.md#build-profile-follow-up-2026-10-28)。

### Perimeter 分片读写锁（16 / 64 分片）

**设想**：将 `Perimeter` 的单表锁拆成按哈希高位路由的 64 或 16 个分片
`RwLock<FastMap<u64, Entry>>`，降低 8 核并发读写前沿表时的锁竞争。

**实测**：在 P2 基线上做交替配对，64 分片与 16 分片在单核和 8 核上均回退约
70–200 ms（Microban 1 核约 +80 ms，XSokoban 1–20 约 +120 ms，Microban 8 核亦慢于
单把 `RwLock`）。

**否决原因**：每次节点扩张通常批量查询/插入 10–30 个子节点哈希。单把 `RwLock` 每次扩张
只需 1 次原子加解锁；分片后同一批子节点分散到十几个分片，变成每扩张 10–17 次原子 RMW
加解锁与跨缓存行跳转，锁扇出开销远大于原本极短的临界区竞争。最终改用单把 `RwLock` 配合
`AtomicUsize` 条目计数（`6741669`）。

**重新评估条件**：核心数扩展到 32+ 线程且通过硬件剖析确认单把 `RwLock` 的写锁等待时间
超过总搜索耗时的 5%，或改用免锁开放寻址表而非分片 `RwLock`。

### 跨关卡保留 Perimeter 哈希表容量

**设想**：在 `Solver` 上跨关卡复用同一个 `Perimeter` 的 `FastMap` 桶数组（只 `clear()`
不释放容量），省去每关重新分配与扩容前沿哈希表的开销。

**实测**：XSokoban 1–20 单核总耗时回退约 +300 ms（8.55 → 8.86 s）。

**否决原因**：大关卡会将 `FastMap` 扩容到数 MB（数十万桶）；随后进入几毫秒就能解出的小关
时，`clear()` 仍需遍历清零或让探测跨越大片冷 L3 内存，破坏缓存局部性，得不偿失。

**重新评估条件**：按关卡规模分档池化（小关只复用小容量表），或改用代数标记免清零的定长表。

### IndexedHeap 维护稠密反向索引 `heap_pos`

**设想**：在 `Tree` 上维护 `heap_pos: Vec<u32>` 记录每个 `ExpansionId` 在优先队列中的下标，
使 `Perimeter` 命中后更新节点优先级时无需线性查找即可 O(1) 定位堆元素。

**实测**：队列调整确实变为 O(1)，但整体单核搜索耗时小幅回退（XSokoban 29 固定 8k 扩张慢约
40–60 ms）。

**否决原因**：堆的 `insert` / `pop` 在 **100% 的扩张迭代**上都会发生，每次 `sift_up` /
`sift_down` 交换元素都额外增加对大数组 `heap_pos[id]` 的随机内存写；而触发堆内重排的
`Perimeter` 命中占总扩张不到 1%。最终采用“先判堆顶 + `rposition` 反向扫描”的免索引方案
（`4b97757`）。

**重新评估条件**：某搜索模式下堆内重排频率提升到总扩张的 10% 以上，且单队列规模持续在
数万元素以上。

### 8 核无停车方案时填充 fallback 正向线程

**设想**：8 核模式下策略 0 与策略 2 若未提取出有效 `parking_order` 会提前退出；让这两个
空闲线程转去跑无规划的 `solve_forward_fallback`，避免核心闲置。

**实测**：Microban 8 核无明显改善，XSokoban 1–30 8 核总耗时回退约 2–4 s。

**否决原因**：无规划正向搜索在大关上几乎不可能比带规划策略先解出，却会持续满载占用物理核、
挤占其余 6 个有效策略线程的 CPU 睿频空间（Turbo headroom）和末级缓存/内存带宽，并加剧共享
`Perimeter` 锁竞争。

**重新评估条件**：有低开销的启发式兜底策略证明能在无 parking order 的关卡上独立解出，且仅在
所有带规划线程均无方案时才启动。

### 内部线性 Zobrist 哈希与增量撤销式子状态步进（P3-B）

**设想**：用编译期生成的 64 位 SplitMix64 线性 Zobrist 表（单缓存行 `low3`、`soko`、
`box_key`、`base_key`、`high2` 及维度种子）替换内部 C++ 多项式哈希 `Board::hash()`（原哈希
保留为 `cpp_hash()` 供差分与 `--analyse` 使用）；同时在 `Helper` 池化 `ChildStepper`，每父
节点单趟拷贝并算出无玩家基准哈希，逐候选步只原位修改 `from`/`to` 两格并在玩家泛洪时增量异或
`soko` 键、评估后按队列回滚，且让 `BaseSearch` 写入 `Perimeter` 时用 1 次 `XOR bases_xor`
替代逐子节点的 `Board` 重建与重泛洪。

**实测**（基于 P3-A `8f32adf` 做 3–5 轮 ABBA 交替配对，对比每轮原始秒数）：

- `Microban` 单核（155 关，扩张均为 `21,925`）：P3-A 五轮 `5.08 / 4.87 / 4.69 / 4.79 / 5.01 s`
  （均 `4.89 s`）vs P3-B `4.94 / 4.90 / 4.91 / 4.47 / 4.79 s`（均 `4.80 s`），仅差 `0.09 s`。
- `XSokoban 29` 固定 8k 正向扩张（单核，扩张均为 `8,000`）：P3-A 五轮
  `3.79 / 3.61 / 3.59 / 3.59 / 3.63 s`（均 `3.64 s`）vs P3-B
  `3.59 / 3.50 / 3.60 / 3.60 / 3.22 s`（均 `3.50 s`），仅差 `0.14 s`。
- `XSokoban 1–20` 单核（扩张均为 `7,939`）：未降频的前两轮 P3-A 为 `8.64 / 8.57 s`，P3-B 为
  `8.27 / 8.08 s`，真实差距仅约 `0.4 s`；后三轮受连续跑批热降频影响跳至 `9.4–10.5 s` 档，
  曾一度造成中位数虚高的假象。
- `XSokoban 1–28` 8 核：P3-A 五轮均 `19.94 s` vs P3-B 均 `19.66 s`（仅差 `0.28 s`）；含第 29
  关的 `XSokoban 1–30` 8 核三轮均值为 `69.04 s` vs `84.28 s`（受第 29 关多线程竞态波动主导）。
- `XSokoban 29` 单核完整求解：无时限确定性模式下 P3-A 三轮 `151.1 / 142.8 / 137.2 s`（均
  `143.7 s`，扩张 `1,057,264`）vs P3-B `150.1 / 145.1 / 129.9 s`（均 `141.7 s`，扩张
  `1,057,071`）；默认限时模式下未降频首轮同为 `124,684` 次扩张，耗时 `64.18 s` vs `62.84 s`
  （仅差 `1.34 s`）。
- 初版若未池化 `ChildStepper` 而在栈上每次构造，还会因每次清零 `5.2 KB` 泛洪队列产生约 3–5%
  的负优化。

**否决原因**：

1. **真实时间收益极小**：经过 P0–P3-A 后，正向与逆向搜索 95% 以上的 CPU 时间都在推拉图 Tarjan、
   固定箱死锁、匈牙利匹配与连通度 BFS 上，子盘面拷贝加原版多项式哈希合计仅占总耗时的 1%–3%，
   即便将该环节降到接近零开销，端到端也只能省下 `0.1–0.4 s`（大关约 1–2%）。
2. **扩张数无收益且破坏内部轨迹等价性**：主搜索队列不按哈希排序，更换哈希不会减少节点扩张；
   反而辅助死锁搜索的 1024 桶独立步估计器（`hash & 0x3ff`）因位分布改变产生轻微截断漂移，使深层
   扩张数不再与 C++ 原版严格一致。
3. **复杂度与体积不划算**：额外引入 550+ 行增量回滚状态机与双哈希接口，并增加约 `329 KiB`
   静态表二进制体积（`1.24 → 1.56 MiB`），投入产出比过低。

**重新评估条件**：后续算法改动（例如引入大规模置换表探测、需要 O(1) 无盘面构造的纯哈希前瞻
剪枝，或推拉图/死锁主瓶颈再降一个数量级使 `Board::hash()` 占比升至 10% 以上）真正依赖可增量
异或的代数性质时再重新启用。
